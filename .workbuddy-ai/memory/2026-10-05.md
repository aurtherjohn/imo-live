## The directive's premise was partly wrong — say so next time
The report was "new phone signups fail with *That number or PIN is incorrect.*"
That exact string exists in **one** place: `_translatePhoneSignIn`. So it can
only come from the **Login** path. The Create-Account branch has called
`createUserWithEmailAndPassword` since the initial commit, and `_fullDigits` was
already fixed in `1388aa5`. Lesson: grep the literal error string before
believing a symptom's stated cause — it localises the path for free.

## Phone signup — the real defect was a dead-end, not the branch
`signUpWithPhone` created the auth account, then wrote the Firestore claim. If
the claim failed and `_rollback`'s `user.delete()` was refused (needs a recent
login), the account **survived holding the derived address with no profile** —
so every later signup got `email-already-in-use` and the number was blocked
permanently. Fix: on that one code, try `signInWithEmailAndPassword` with the PIN
the user just typed (same number + same PIN = same person) and adopt the
account; the claim + `_createUserDocument` are `merge:true`, so re-running is
idempotent. ⚠️ **Never `_rollback` a *recovered* account** — that deletes the
caller's own account. Guarded with `if (!recovered)`.

## Email verification is a LINK, not a code
`otp_screen.dart` had six digit boxes for a flow that sends a link. Rewrote it
in place (route `AppRoutes.otp` and the gate's redirect are unchanged — only the
screen's contents changed): instructions card, 60 s resend, "I've confirmed my
email", 5 s `user.reload()` poll. `sendEmailVerification` now takes
`ActionCodeSettings(url: 'imo://verify-email', handleCodeInApp: false, ...)`.
⚠️ **`handleCodeInApp` must stay false** — that flag is for email-link *sign-in*;
verification has to run on Firebase's hosted page because the client cannot see
the link. ⚠️ An unauthorised continue URL makes the send **throw**
`unauthorized-continue-uri` (it does not silently drop the URL), so
`_sendVerification` retries with a plain send — verification must never fail
over a redirect. Manifest gained a second intent-filter on the existing `imo`
scheme (`host="verify-email"`).

## Follow-up pass — the new test found a real bug
Added `test/features/email_verification_screen_test.dart` (guards "no code boxes"
+ the resend cooldown). It failed on the first run, and not for a test reason:
`AuthPrimaryButton`'s label `Row` is `mainAxisSize.min` inside a `Center`, so a
non-flexible child is given **unbounded width** — `I've confirmed my email`
overflowed by 25 px at 420 dp. Fixed in the shared widget with
`Flexible(child: FittedBox(fit: BoxFit.scaleDown))`, which bounds the width and
scales the label down instead of overflowing.

⚠️ This was latent for **every** long CTA, and worse in `bn` where labels are
longer; short English labels ("Verify", "Login") hid it. `scaleDown` never
enlarges, so buttons that already fit render at natural size — no visual change.
Lesson: a widget test that only pumps a screen and asserts
`takeException() == null` earns its keep.

## ⚠️ APK size is NOT a "did my change ship?" signal — compare digests
`build-25` and `build-27` have **byte-identical sizes** (131671715 / 106337467 /
116347050) but **different sha256 digests**. Cause, confirmed by reading the ZIP
central directory over HTTP Range: every `.so` is `STORED` (uncompressed, ratio
1.000) and page-aligned, so a small Dart delta that does not cross a 4 KiB
boundary leaves the padded total unchanged.

```
all .so total : 108.9 MB   libapp.so : 12.8 MB   libflutter.so : 11.2 MB
apk total     : 125.6 MiB (arm64-v8a)
```

So: **diff the asset digest, never the size.** A size that did not move proves
nothing. (Method: fetch the last ~3 MB with `Range: bytes=<start>-<end>`
— ⚠️ a suffix range `bytes=-N` returns **501** on
`release-assets.githubusercontent.com` — then walk the central directory. For a
private repo, get the signed URL from `/releases/assets/{id}` with
`Accept: application/octet-stream` and fetch it **without** the auth header.)

### Remote tracking ref is stale by design
`refs/remotes/origin/main` sits at `5b56d32` — the **remote sha of `5a67d79`** —
because the Git Data API path never updates it. The API also assigns a *different*
commit sha than the local one for identical content (local `60166c8` / remote

always pass `DIFF_BASE=<local parent sha>` to `push_via_api.mjs` rather than
letting it fall back to the stale `origin/main`.
