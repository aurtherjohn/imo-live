## Phone signup — the real defect was a dead-end, not the branch
`signUpWithPhone` created the auth account, then wrote the Firestore claim. If
the claim failed and `_rollback`'s `user.delete()` was refused (needs a recent
login), the account **survived holding the derived address with no profile** —
so every later signup got `email-already-in-use` and the number was blocked
permanently. Fix: on that one code, try `signInWithEmailAndPassword` with the PIN

account; the claim + `_createUserDocument` are `merge:true`, so re-running is
idempotent. ⚠️ **Never `_rollback` a *recovered* account** — that deletes the
caller's own account. Guarded with `if (!recovered)`.

Four consecutive CI runs failed while bringing the release keystore into Actions.
Runs #30/#31/#32 all died at **configuration**, ~2 min in, with:

```
Could not create an instance of type
com.android.build.api.variant.impl.ApplicationVariantBuilderImpl

    .../android/app/build.gradle.kts
* Where: Build file '.../android/build.gradle.kts' line: 32
```

`namespace = "com.imo.live"` **was** present. Line 32 is
`subprojects { project.evaluationDependsOn(":app") }` — root-file, unchanged
since the initial commit, so not the variable.

### Diagnostic method that actually worked
Differential against the **real CI revisions**, fetched via the Git Data API
(`/commits/<sha>` → `commit.tree.sha` → walk `android/app/build.gradle.kts` blob
→ `Accept: application/vnd.github.raw`). Local `git show` is useless here — the
API commits have different shas.

| revision | `import java.io.File` | outcome |
|---|---|---|
| `b268a007` (#29) | **absent** | configured fine, died later at `validateSigningRelease` |
| `145cedc2` (#30) | present + `File?` val | **namespace failure** |
| `42c28fb` (#31) | present, val → `String?` | namespace failure |
| `c15dde0` (#32) | present, resolution deferred into functions | namespace failure |

The import is the only thing common to every failure and absent from the success.
**Corrected twice:** first I blamed a `File`-typed top-level `val` (wrong — #31
renamed it and still died), then "resolving `rootProject` at constructor scope"
(wrong — renamed into functions, still died, and the *pristine* initial commit
touches `rootProject.file()` at top level and built for weeks).

Mechanism: `evaluationDependsOn(":app")` forces this script to compile+configure
early; importing `java.io.File` changes how the generated Kotlin-DSL script class
resolves its `Project` delegate, so AGP builds the `android {}` extension before
`namespace` is applied.

### The fix
Drop the import; spell `java.io.File` **fully-qualified** at the three points of
use; return the resolved path as a **String**. Restores #29's proven structure and
changes only the path arithmetic (`rootProject.file(path)` for the env-var source,
which is what fixes #29's doubled-path bug: `file()` inside `android {}` is
*-module*-relative, so a repo-root-relative `KEYSTORE_FILE` concatenated to
`android/app/android/app/...`).

Keystore half was never the problem: runs #29–#32 all printed SHA-1
`AA:09:94:7E:42:5C:05:53:B0:AA:D7:09:08:25:1B:94:E0:B8:C4:56` and SHA-256
matching the Firebase-registered pair exactly, and the file decoded to 2748 bytes.

### CORRECTION (later the same evening) — it was never the import, nor rootProject
Five runs (#30-#34) died on this. Four separate "fixes" from inside the script
all failed, including removing **every** `rootProject` reference. The real
variable is **AGP 9.1.0 + `android.newDsl=false`** (both in
`android/gradle.properties`): doing *any* path arithmetic at configuration
scope in this module makes AGP build `ApplicationVariantBuilderImpl` before the
namespace is registered. Run #29 configured fine because it did none — it
assigned `storeFile` straight from a constructor-time String.

⚠️ **Never do path arithmetic in `android/app/build.gradle.kts`.** Resolve the
path where the value is produced instead: the CI build step now exports an
**absolute** `KEYSTORE_FILE: ${{ github.workspace }}/android/app/imo-live-release.jks`,
so `file()` has nothing to mangle and run #29's doubled-path bug cannot recur.
The script is byte-identical to #29 apart from one execution-phase guard in
`assertReleaseSigning.doFirst` that rejects a relative `KEYSTORE_FILE` early.

Lesson: when a config-time failure resists several hypotheses, stop editing the
file the error *names* and check `gradle.properties` / plugin versions for a
compatibility flag that changes the failure mode.

### ⚠️ The killer: `set -e` + a failing command substitution = silent exit 1
Step 13 `Verify signed APK certificate` failed in **0.7 s with zero output**.
Cause, reproduced locally three ways and now fixed:

```bash
# GitHub runs this as `bash -e`. grep exits 1 on no match, pipefail propagates
# that as the pipeline status, and -e aborts AT THE ASSIGNMENT — before the
# echo on the next line. Exit 1, no output, no clue which command died.
APK_SHA1=$(grep -i 'SHA1:' apk-cert.txt | head -1 | sed ... | xargs)
echo "APK SHA-1 : $APK_SHA1"     # never reached
```

| variant | result |
|---|---|
| no-match + `pipefail` + `-e` | **exit 1, zero output** ← the bug |
| match + `pipefail` + `-e` | fine |
| no-match, no `pipefail` | survives, var empty |

**Rule: never combine `set -e` / `bash -e` with `$(grep …)`, and always append
`|| true` to a grep used for parsing.** Guards must decide success and must say
*why* they failed. Both `Verify keystore fingerprint` and `Verify signed APK
certificate` now use `set -uo pipefail` (no `-e`) + `|| true` + explicit
empty-value diagnostics, and resolve `keytool` via `$JAVA_HOME/bin/keytool`
with a `command -v` fallback.

Lesson: GitHub's own `shell: /usr/bin/bash -e {0}` is easy to forget — a step
script starts with `-e` whether or not you asked for it.

## ✅✅ THE ACTUAL FIX (runs 38 → 40): `keytool` cannot read a v2/v3-signed APK

Run 38 fixed the `set -e` blindness and *immediately named the real cause*:
`keytool -printcert -jarfile` exits 0 and prints the literal string
**`Not a signed jar file`** — with no `SHA1` anywhere in it.

**Why: this app is `minSdk = 24`.** At minSdk >= 24 AGP **disables v1 (JAR)
signing by default** and signs with **APK Signature Scheme v2/v3 only**.
`keytool -printcert -jarfile` reads *v1 JAR* signatures exclusively (its own
help: `-jarfile <file>  signed jar file`). So the tool is structurally blind to
the artifact. Proven locally with a real APK built by `aapt` and signed both
ways:

| APK scheme | `keytool -printcert -jarfile` |
|---|---|
| v2/v3 only (ours) | exit 0, `Not a signed jar file`, **0 SHA1 lines** |
| v1 + v2/v3 | exit 0, full certificate, 1 SHA1 line |

**The right tool is `apksigner verify --print-certs`** (Android SDK
build-tools). It reads v2/v3 *and* v1, and prints lowercase colon-less hex:

```
Signer #1 certificate SHA-1 digest: aa09947e425c0553b0aad70908251b94e0b8c456
```

so comparison must `tr -d ':'` **both** sides — raw string compare always fails.

### ⚠️⚠️ apksigner's label is NOT stable across build-tools
The cause of run 40's failure, on an APK whose key was **CORRECT**:
- build-tools 35/36 → `Signer #1 certificate SHA-1 digest: …`
- build-tools **37.0.0** → `V2 Signer: certificate SHA-1 digest: …`

Run 40 was on `build-tools/37.0.0`; grepping for `Signer #1` produced an empty
value and a **false failure**. **Never anchor on `Signer #1`** — match the
invariant substring `certificate SHA-1 digest`. (A useful aside: run 40's log
dumped the real certificates, proving the release key IS correct —
SHA-1 `aa09947e…` == `AA:09:94:7E:…:C4:56`, SHA-256 `57fbd960…` ==
`57:FB:D9:60:…:33:87`. Signing was never broken.)

Other traps hit while hardening this step:
- `${VAR:-}` for `ANDROID_HOME` / `ANDROID_SDK_ROOT`: under `set -u` a bare
  reference aborts with "unbound variable".
- apksigner discovery must accept a **non-executable** candidate (`[ -e ]`, not
  `[ -x ]`): a Windows SDK ships only `apksigner.bat` with no exec bit.
- Give node/MSYS tools Windows-form paths for `.bat`/`.exe` (`cygpath -w`) —
  MSYS `/c/...` paths are not understood by them.

Method that carried this: extract the step's shell from the YAML, run
`bash -n`, then execute it against a **real v2/v3-signed APK** with 4 cases
(match / SHA-256-only mismatch / SHA-1 mismatch / tool-missing). Local proof
beats another 17-minute CI cycle.
