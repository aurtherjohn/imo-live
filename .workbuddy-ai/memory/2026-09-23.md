# 2026-09-23 — Imo LIVE: real root cause of the black screen, found and fixed

## TL;DR
The 2026-09-22 session *believed* it had fixed the black screen (it blamed a
stubbed `main.dart`). It had not. Two independent bugs were still live, and the
launch test that would have caught them was **failing** — the previous session's
"all tests passed" claim was no longer true at the start of this session
(128 passed, **2 failed**, both in `test/startup/app_launch_test.dart`).

## ROOT CAUSE 1 — `main()` awaited storage *before* `runApp` (the black screen)
Reproduced and proven with a throwaway diagnostic test:

```
DIAG pathProvider done=false err=null      <-- never completes, never throws
DIAG hiveInitFlutter done=false err=null   <-- never completes
DIAG init done=false ready=false           <-- LocalDatabase.init() hangs
DIAG bootstrap done=false err=null         <-- so bootstrapProvider never finishes
```

`LocalDatabase.init()` -> `Hive.initFlutter('imo_live')` ->
`getApplicationDocumentsDirectory()`. That platform call **never completes** (it
does not throw — it just never answers). `main()` was:

```dart
final bool storageReady = await _initStorage();   // <-- hangs forever
runApp(...);                                      // <-- never reached
```

Nothing renders, nothing crashes, and the Android window sits on
`@color/imo_background` = `#FF0B0B0D` — **a black screen, forever.** Exactly the
report.

### Fixes
- `lib/main.dart` — **no `await` anywhere before `runApp`**. Storage init moved
  entirely into the widget tree. `runApp` is now unconditional.
- `lib/local/database/local_database.dart` — `init()` can no longer hang or
  throw:
  - `Hive.initFlutter` bounded by a 3s timeout; each box by 800ms.
  - `init()` returns a **shared in-flight future** (`_initializing`), so
    concurrent callers cannot race into opening the same box twice.
  - `Hive.isBoxOpen` moved **inside** a try/catch — it throws `HiveError`, which
    is an `Error` not an `Exception`, so it used to escape `init()` and abort
    startup.
- `lib/features/misc/presentation/startup.dart` — outer 6s ceiling on
  `init()`, and it now publishes `storageReadyStateProvider` +
  `startupFailedProvider`.
- `lib/features/chats/presentation/providers.dart` — `storageReadyProvider` was
  a hardcoded `true` (a lie whenever storage failed) and `storageDegradedProvider`
  was never rebuilt. Both now derive from `storageReadyStateProvider`.
- `chats_screen.dart` — new `_StorageWarningBanner`. `startupFailedProvider` was
  **set but never read by any screen**, so a device with unreadable storage
  silently showed an empty chat list. Now there is a warning + a working Retry.

## ROOT CAUSE 2 — GoRouter shadowing (three dead-end navigations)
`router_test.dart` only asserts paths are *registered*, never that they
*resolve*. GoRouter takes the **first** match in declaration order, so the
parameterised routes declared early swallowed their static siblings:

| Path | Resolved to | Should be |
|---|---|---|
| `/chat/search` | `ChatScreen(id: "search")` | `ChatSearchScreen` |
| `/contact/select` | `ContactInfoScreen(id: "select")` | `SelectContactScreen` |
| `/contact/new` | `ContactInfoScreen(id: "new")` | `NewContactScreen` |

`selectContact` is pushed from the Profile screen, the Calls screen (3 places)
and the Chats empty state; `newContact` from the drawer and the contact picker;
`chatSearch` from the chat screen. All three were broken user-visible dead ends.

### Fix
All `/:id` detail routes (`chat`, `contactInfo`, `groupInfo`, `community`,
`channel`) moved to the **bottom** of the route list, after every static path.
New `test/app/route_resolution_test.dart` pumps each URL through the real router
and asserts which screen renders — this is what registration checks miss.

## Two real bugs found and fixed this session

### 1. `launch_mark.xml` had `--` inside an XML comment (broke the debug build)
```
[Fatal Error] launch_mark.xml:7:5: The string "--" is not permitted within comments.
Execution failed for task ':app:parseDebugLocalResources'.
```
The decorative underline `----------------` (hyphens) inside the XML comment is
illegal — XML forbids `--` anywhere in a comment body. Removed the dash run.
**Lesson: this file is a recurring landmine because it is heavily commented.**
Validate with a parser, not by eye:
`python -c "import xml.etree.ElementTree as ET; ET.parse(f)"` — all 6 res XMLs
now parse clean.

### 2. `ink_sparkle.frag` shader missing in widget tests
`app_theme.dart` sets `splashFactory: InkSparkle.splashFactory`. First tap on any
`Material` widget lazily loads `shaders/ink_sparkle.frag`, which is NOT in the
test asset manifest → `Asset 'shaders/ink_sparkle.frag' not found`.

**Diagnostic that settled it** (two-case test): an `InkWell` *with* a `Material`
ancestor THREW; one *without* PASSED. So the failure comes from the splash
needing an ink controller to paint onto — NOT from a missing Material ancestor
(that was my first, wrong hypothesis). With no Material host there is nothing to
paint, so the shader is never requested.

**Fix:** in `pumpThemed` (test/widgets/widget_smoke_test.dart) override *only*
the splash factory, keeping every other theme value real:
```dart
final ThemeData theme = AppTheme.dark().copyWith(
  splashFactory: InkSplash.splashFactory,
);
```
Flutter's own `ink_sparkle_test.dart` carries `@Tags(['reduced-test-set'])` and
is excluded from normal CI for the same reason — that is the precedent.

**Also improved the source:** `SettingsTile` used a bare `InkWell` with no host;
now wrapped in `Material(type: MaterialType.transparency)` so the press ripple
actually renders in any context.

**Shrinking the AVD does NOT work for API 37.** Tried all of:
- `disk.dataPartition.size=1500M`, `sdcard.size=64M`, `hw.ramSize=1536M` in

Also note: deleting `build/app/intermediates` (2.4 GB per `du`) freed **~0 MB** —
`C:` went 2646 MB → 2338 MB free. That 2.4 GB was apparently already counted
elsewhere / hardlinked. Do not count on reclaiming intermediates to make room.

~2.3 GB free vs a 7.3 GB requirement. Deleted the AVD, left the environment as
found. All four APKs were backed up to `tiger/apk_backup/` (byte-verified with
`cmp`) before touching intermediates, so the deliverables are safe.

The `apk_backup/` directory was added this session — it duplicates
