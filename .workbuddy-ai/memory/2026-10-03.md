# Phone + PIN sign-in, and the end of Facebook (Task B)

Second task of the day. Login screen: Facebook out, "Continue with Phone" in.
New phone sign-up / sign-in screen. `flutter analyze` clean, full suite
**422 passed / 9 skipped / exit 0** (was 406 — the 16 new tests all pass).

## WARNING: the spec's core design was rejected — read before "fixing" it back

The request asked for **`passwordHash` + `salt` computed client-side and stored
on `users/{uid}`**, plus a `phone_index/{number}` collection, and explicitly
"DO NOT use Firebase Auth". **None of that was implemented.** Reasons:

1. **A 6-digit PIN cannot be safely hashed anywhere the client can read.**
   10^6 candidates is under a second of GPU work. Against a leaked salt+hash the
   attacker enumerates the whole keyspace *offline* — no rate limit, no network.
   No KDF setting fixes a secret that small; only a server that refuses to answer
   fast does, which is exactly what the auth backend is.
2. **The deployed rules grant every signed-in user read on every document**
   (`if request.auth != null` on `/{document=**}`). A hash on `users/{uid}` would
   therefore be *published to every account in the app*.
3. **"No Firebase Auth" breaks the app.** `auth_gate.dart` is driven by
   `User?` from `authStateChanges()`, and `currentUidProvider` feeds every chat,
   contact and profile read. A local-only session means rewriting the gate and
   every consumer. And a signed-out client **cannot read Firestore at all** under
   the deployed rules, so an index-based phone login could not even look up the
   number.
4. **Firebase Auth email/password is free on Spark.** The "avoid the pro plan"
   constraint was about *SMS*, which this design never needs.

### What was built instead — the derived-address trick

`AppConstants.phoneAuthEmailFor('8801712345678')` ->
`p8801712345678@phone.imolive.app`, and the **PIN is the Firebase Auth password**.
So the backend salts and hashes it and **nothing password-derived is stored in
Firestore at all**. Three properties fall out of the address being *derivable*:

* **A signed-out login needs zero Firestore reads** — the client computes the
  address locally. This is the only thing that makes phone login possible under
  `request.auth != null`.
* **Uniqueness needs zero pre-signup reads** — `createUserWithEmailAndPassword`
  returns `email-already-in-use` when the number is taken.
* The atomic claim of `phones/{digits}` + `usernames/{handle}` is a
  **transaction** (`_claimPhoneIdentity`), so two simultaneous signups cannot
  both win.

`phone_index` was **not** created: the existing `phones/{digits}` collection
already is that index, is already written by email signup, and is already read by
search. A second one would be a second source of truth.

## WARNING: the gate had to change, and it is the non-obvious bit

### ⚠️ Real bug found in `firestore.rules` — `{document=**}` matches ZERO segments

`match /users/{uid}/{document=**}` **also matches `/users/{uid}` itself.** Rules
are OR'd, so that permissive subcollection branch re-opened the parent profile to
every signed-in user and made `isSelf()` + `noPasswordMaterial()` **dead code**.
The emulator returned **200** for a write of `{passwordHash: …}` to *another*
user's profile.

This is the same trap the file's own header warns about, one level down. Fixed by
requiring a real segment:

    match /users/{uid} {
      allow read: if signedIn();
      allow create, update: if isSelf(uid) && noPasswordMaterial();
      allow delete: if isSelf(uid);
      match /{sub}/{doc=**} { allow read, write: if signedIn(); }   // {sub} is load-bearing
    }

Applied to all 9 app-data collections too (behaviourally identical there today,
but it is the identical trap waiting for whoever tightens them).

⚠️ **Lesson: a rules file that reads correctly can still not be enforced.** The
only thing that caught this was running the emulator. Reading the file back,
linting it, and `flutter analyze` all pass on the broken version.

### Emulator gotchas (all three cost real time)

- **"Signed out" = no `Authorization` header.** `Bearer garbage` → **400
  `invalid jwt`** from the transport, never reaching the rules engine. Only a
  header-less request gives the 403 that proves `signedIn()` is false. My first
  harness asserted 403 on a bogus token and reported 9 false failures.
- **`Bearer owner` is an admin bypass** — rules skipped. Fixtures only.
- **Any decodable JWT is trusted**, including `alg: none`. A hand-made token
  cannot impersonate a user.
- `firebase.json` needs an `emulators` block or `--only auth` refuses to start;
  `java` must be on `PATH` (`<android studio>/jbr`).
- A stale emulator keeps the port; killing the CLI wrapper does **not** kill the
  `java`/`node` children. Check the port before restarting.
- The harness must randomise its ids per run, or the second run hits
  `EMAIL_EXISTS`, gets no `localId`, and fails everywhere on `undefined`.

### Test-harness gotcha worth remembering

`find.text('Create Account').first` taps the **`_ModeSwitch` pill**, not the
submit button — the mode switch renders the same label, and tapping an
already-selected segment does nothing. All 8 new tests silently read an empty
capture until this was fixed. Use
`find.widgetWithText(AuthPrimaryButton, label)`. Also: `AuthScaffold` scrolls, so
`ensureVisible` before `tap` or the button is below the fold.

## 2026-10-03 (later still) — audited the rules against call sites; a SECOND deploy-breaking bug

Before deploying, ran the skill's Step 1: enumerate every collection from the
code and check it is in `firestore.rules`. A deploy with a collection missing
would **deny** it (fail-closed), breaking that feature.

Resolved: `calls`, `chats`, `messages`, `users`, `list`, `status`, `contacts`,
`points_transactions`, `notifications`, `usernames`, `phones`, `emails`,
`channels`, `channel_usernames`, `channel_keys`, `posts`, `reactions`,
`followers`, `join_requests`, `analytics`. All covered.
- The dynamic `db.collection(collection)` in `remote_contact_service._resolve` is
  only ever called with `phones`/`emails`/`usernames` — safe.
- ⚠️ `channel_service.dart:765` runs `db.collectionGroup('reactions')`.

### The bug: a collection-group query is NOT provable by a path-scoped rule

    FAIL  a signed-in collectionGroup("reactions") query is ALLOWED
          -- status=403 {"message":"No matching allow statements"}

`match /channels/{id}/{sub}/{doc=**}` matches those exact documents and is still
rejected, because a collection-group query spans parents the rule cannot pin
down. Firestore rejects the **whole query**, so `ChannelService.watchMyReactions`
would have stopped loading reaction state across every channel feed — silently.

Fixed with a root-anchored rule:

    match /{path=**}/reactions/{reactionId} { allow read: if signedIn(); }

`read` only: reactions are written via `postRef.collection('reactions')` under a
concrete channel, which the `channels` block already covers. Asserted both ways.

Harness now **46 assertions, 0 failures, exit 0**. The query returns 2 docs across
two parents, proving the wildcard matches at both depths.

⚠️ **Two separate bugs, both invisible to analyze/lint/re-reading, both found only
by running the emulator.** Neither would have been caught by a code review of the
rules file. Do not deploy a ruleset without running it.
