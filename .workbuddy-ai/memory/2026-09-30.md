## Firestore rules draft — written for review, NOT deployed

The deployed rules are `match /{document=**} { allow read, write: if
request.auth != null; }` — any signed-in user can read and write every document
in the database. Offered a per-collection ruleset; produced
**`firestore.rules.draft`** (459 lines) in the project root.

**Method — the model came from call sites, not from guessing.** Grepped every
`.collection(` in `lib/`, then read the write payload at each one to find the
field that identifies the owner. 13 top-level collections, 8 subcollections.

**The finding that matters most is a rules-vs-query trap, not a rule.** A rule
that reads *another* document — `exists(channels/x/followers/uid)` or
`get(...)` — is fine on a **subcollection** rule (the query is already scoped to
that path, so the condition is identical for every candidate document), but
**cannot be satisfied by a collection-level query that does not filter on the
same condition**. Firestore rejects the whole query with "Missing or
insufficient permissions". Two rules had to be deliberately weakened because of
it:

- `channels/{id}` read is `signedIn()`, not "owner or member or public" —
  `watchChannelsForMonetization()` queries `where monetizationStatus == pending`,
  which proves nothing about privacy. The channel *document* is therefore
  public directory metadata; the **posts** are what carry the membership rule,
  and those are a subcollection, so they ARE protected.
- `status/{id}` read is `signedIn()`, not "me or my contacts" — `watchStatuses()`
  queries `where userId whereIn [30 uids]`. Making it strict needs a fan-out
  feed, not a rule.

**Six rules are deliberately permissive and marked `LOOPHOLE` in the file**,
each with the app change that would close it: `users` field exposure (rules
cannot hide fields — needs a `profiles` split), client-authoritative points on
both sides of a gift, the email/phone enumeration oracle, the status feed, the
client-reported `followerCount`/analytics, and the `channel_usernames` /
`channel_keys` create path — which **cannot** be ownership-checked at all,
because `createChannel()` writes the channel and its indexes in one batch, so
the channel does not exist when the rule runs. Plus GAP 7: `calls` has no TTL,
so a call whose client died mid-ring stays `ringing` forever.

**`_fstest/lint_rules.py` (new)** — structural lint: brace/paren balance, `allow`
verbs, match blocks with no allow, undefined/uncalled helpers. Not a compiler
substitute; it catches the hand-editing mistakes that would deny every request.
Its own first two versions were wrong (a non-greedy regex that stopped at a
nested `function`'s closing brace; then `text.index("{")` picking up the
`{database}` path wildcard instead of the block brace) — the fix is to take the
**last** character of the match regex as the block opener.

⚠️ **Syntax is lint-checked but NOT validated by the Firebase compiler.**
Creating an unreleased ruleset via `projects.rulesets.create` would validate it
without changing what is served — offered, not done, because the standing
instruction is *do not deploy* and that call still writes to their project.

### ⚠️ The ad stack owns its timers — this is what broke the test suite

`flutter test` failed 3 tests in `test/startup/app_launch_test.dart` with *"A Timer is still pending
even after the widget tree was disposed"*, and my first guess (the auth-gate change) was **wrong** —

## l10n: the "28 residual literals" was wrong — it was 189

The counter (`_l10n_scan.py`) and the converter disagreed by 148 literals and neither failed. Three
independent bugs, all under-counting, all fixed:

⚠️ **`bin_watchdog.py` was silently sweeping nothing, and I fixed it.** Its `--scope` comparison was

then took `C:` from 1.29 → 6.21 GiB in seconds. Documented in the skill's SKILL.md, including the
general lesson: **a broken filter and an empty directory produce identical output — list the pool
before concluding it is empty.**

**2. A `&`-backgrounded build gets reaped.** `(./run_flutter.sh build ... > log 2>&1; echo EXIT=$?) &`

## Firestore rules: re-verified the draft against the current tree, found 4 bugs

`firestore.rules.draft` already existed (written 2026-09-29) but the app had changed since
(delete-for-everyone, l10n, ads). Re-derived the data model from the call sites again and found four
defects, two of which would have broken a feature:

- **`channelIsPrivate()` tested `secretKeyHash != ''` as a proxy for privacy.** `Channel` carries
  BOTH `isPublic` and `secretKeyHash`, and `isPublic` is what the UI branches on
  (`bool get isPrivate => !isPublic`). An approval-gated private channel has `isPublic: false` and an
  **empty** `secretKeyHash` → the proxy called it public, so its posts were readable by anyone.
  Now tests `isPublic` directly (both fields are in `Channel.toJson`).
- **The `messages` update rule was sender-only** (`resource.data.senderId == uid()`). But
  `markChatRead()` and `updateMessageStatus()` are driven by the **recipient** and rewrite a message
  they did not send. Every read receipt would have been denied — and **quietly**: `markChatRead()`
  catches the error and falls back to clearing only the caller's own counter, so the badge would stop
  clearing on the other device with nothing in the logs. Now non-senders may write only
  `['status','deliveredAt','readAt']`.
- **`reactions` read was `signedIn()`** — leaks the reaction graph. The only query is a
  **collection-group** `where('uid', == uid)`, which *implies* `resource.data.uid == uid()`, so
  own-only is both tighter and still provable.
- **`chats` delete was allowed for any participant.** No call site deletes a chat document —
  `firestore_chat_service.dart` has exactly one `.delete()` and it is `deleteContact()`. Now denied.

⚠️ **`viewCount` IS written by viewers** (`recordPostView`, channel_service.dart:751) — the posts
update rule must allow `['viewCount','reactions']` for a non-owner. Worth checking before tightening.

### The rule that decides outages

A rule that reads another document cannot be satisfied by a query that does not filter on the same
condition — Firestore then rejects the **entire** query. All **thirteen** queries in `lib/` were
enumerated and checked to imply their rule. Two are load-bearing and must NOT be "tightened":

- **`channels` read = `signedIn()`** — forced by `watchPendingMonetization()`'s
  `.where('monetizationStatus', == 'pending')`, an unfiltered collection query. A membership rule here
  would break the admin queue for everyone.
- **`users` read = `signedIn()`** — forced by `RemoteContactService.search()`'s prefix range query.
  Owner-only would break name/username search.

⚠️ **Query #11 (`join_requests`) is provable ONLY because a widget guards it.**
`_OwnerTools.build()` returns early with `if (!isOwner) return const SizedBox.shrink();` **before**
watching `channelJoinRequestsProvider`. That is the only thing keeping the unfiltered list provable
for an owner. Recorded as GAP 8 with the structural fix (mount the count in a child that only exists
in the owner branch).
