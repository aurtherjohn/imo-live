### Fixed: the last two `flutter test` failures

`test/startup/app_launch_test.dart` (splash → `ShellScreen`) failed with
`Expected: true / Actual: <false>`.

Root cause: `authRedirect` in `lib/app/auth_gate.dart` holds at the splash while
`_resolved == false`, and the **only** thing that ever set `_resolved = true` was
`resolveAuthWithoutFirebase()` in `lib/main.dart`. A widget test pumps
`ImoLiveApp` directly and never runs `main()`, so the gate stayed unresolved
forever and every `context.go(AppRoutes.chats)` was bounced back to `/splash`.

Fix: the gate now owns its own resolve clock.

```dart
const Duration _authResolveDeadline = Duration(seconds: 3);
Timer? _deadline;

void _startDeadline() {
  _deadline ??= Timer(_authResolveDeadline, () {
    if (_resolved) return;
    _currentUser = null;
    _resolved = true;
    authRefreshListenable.refresh();
  });
}
```

`authRedirect` calls `_startDeadline()` on the unresolved branch.
`publishAuthState` and `resolveAuthWithoutFirebase` cancel it. Result:
**134 passed, 0 failed.**

## BIG ONE: `flutter.bat` silently exits 0 on this host

**Symptom.** `flutter test` produced *zero* output and exit code 0. A
deliberately-failing probe test also exited 0, proving no test ran at all.
`flutter build apk` would have silently built nothing. `flutter analyze` and
`flutter pub get` worked, which made this very confusing.

**Root cause.** Invoking the tool from bash means the Dart process never sees
`PATHEXT` — a `cmd.exe`-only variable. `package:process` dereferences it
unconditionally when resolving an executable on Windows:

```dart
// process-5.0.5/lib/src/interface/common.dart:60
extensions = platform.environment['PATHEXT']!.split(pathSeparator);
//             ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ throws on null
```

So every command that spawns a child process (pub, the analyzer server, the
Gradle build) dies with `Null check operator used on a null value` before doing
any work.

**Fix — `run_flutter.sh`.** Calls the tool the way `flutter.bat` line 74 does,
bypassing the batch layer, with `PATHEXT` supplied:

```bash
dart.exe --packages="C:/flutter/packages/flutter_tools/.dart_tool/package_config.json" \
         "C:/flutter/bin/cache/flutter_tools.snapshot" "$@"
```

The snapshot path **must** be Windows-style (`C:/...`); Dart resolves it as a
file URI and rejects `/c/flutter/...`. The script also unsets the proxy vars,
sets `PROGRAMFILES(X86)`, and sets `JAVA_HOME` + `GRADLE_USER_HOME`.

### Other environment facts confirmed

- `flutter test` needs the proxy vars **unset** (they hijack the loopback
  WebSocket to `flutter_tester`).
- `flutter analyze` / `flutter test` need `PROGRAMFILES(X86)` or the Dart VM
  aborts.
- Builds need `GRADLE_USER_HOME=<project>/.gradle_home` (which carries
  `org.gradle.daemon=false`) and `JAVA_HOME=…/Android Studio/jbr`. The daemon is
  a detached process whose sandbox policy is enforced independently, so it gets
  `Access is denied` writing under `caches/<ver>/transforms`.
- `cmd.exe` is blocked by the sandbox from bash; PowerShell is available but
  needs git on PATH.

## Disk: deletions go to the Recycle Bin, so `df` never moves

`rm -rf` / `Remove-Item` on this machine move files to `C:\$Recycle.Bin` instead
of unlinking them. That produced a very confusing symptom:

- I deleted ~5 GB (global `~/.gradle`, legacy `.gradle-home`, partial backups).
- `df -h /c` did **not move at all** — still 0 bytes free.
- A 1 MB write still failed with "There is not enough space on the disk".

The space was real; it was just sitting in the Recycle Bin. `$Recycle.Bin` had
grown to **15.49 GB / 165,608 files**.

**Fix:** `Clear-RecycleBin -DriveLetter C -Force` → **15.94 GB free**.

So on this host, always empty the Recycle Bin after bulk deletions, or `df`
will lie to you and you will conclude the filesystem is broken.

Also note: the `rm` shim (`safe-delete`) needs to write a state file into
`%TEMP%\codebuddy-safe-delete-bulk\` **before** it deletes anything. On a
completely full disk that write fails with `ENOSPC`, so `rm` silently does
nothing. Use PowerShell `Remove-Item` instead when the disk is full.

## The `.lock` denials (intermittent, sandbox)

Three attempts died configuring a plugin project with
`java.util.concurrent.TimeoutException` or
`FileNotFoundException: ...transforms/<hash>/<hash>.lock (Access is denied)`.
The transform hash changes every run, so the lock files can't be pre-seeded.

Proved it is process-scoped, not filesystem: the Bash tool can create, write and
read `.lock` files in the exact directories Gradle is denied. So the sandbox is
restricting the Gradle **JVM** (a grandchild process), not the path.

Mitigations that are now in `.gradle_home/gradle.properties`:
`org.gradle.vfs.watch=false`, `org.gradle.parallel=false`,
`kotlin.compiler.execution.strategy=in-process`.
**Do NOT add `org.gradle.configuration-cache=true`** — Flutter's
`:app:DebugMinSdkCheck` task can't be serialised into the config cache and the
build fails with a worse error.
