## Phase 2 — call leak: root cause found
**The teardown was already correct.** `_teardown()` stops every track, disposes the stream,
closes the PC, nulls both `srcObject`s, clears ICE, writes the terminal status.

The real defect: **`_isVideo` was sticky on a session-lived singleton.**
`callServiceProvider` is a plain (non-autoDispose) `Provider` watched by the shell and the
microphone gate, so one `WebRtcCallService` serves every call in a signed-in session.
`_isVideo` was set by the first call and never cleared, so after any video call
`_prepareRenderers()` would re-init the camera renderers and `_openMedia()` would request
`video: true` — i.e. **a later voice call opened the camera.**

Fix: `_startedFromClean()` (line ~290), called at the head of `start()`; `acceptIncoming()`
clears only the camera flags (it must NOT clear `_isVideo` — it derives the kind from the doc).
`_teardown()` sets `_tornDownOnce = true` last.
Also added `didChangeAppLifecycleState` on the call screen (detached only — `paused` is left
running on purpose, backgrounding a call is normal).

⚠️ **Honest limit:** the camera-release itself is **NOT device-verified.** `flutter_tester`
has no `flutter_webrtc` plugin, so `RTCVideoRenderer.initialize()` throws and `_renderersReady`
never turns true — the renderer path is unobservable in tests. Three tests were written; **two
were discarded because they passed with the fix disabled**, i.e. they proved nothing.
The surviving 8 (`webrtc_call_permissions_test.dart`) assert the permission gate and teardown
contract only. Treat "camera LED off after a call" as **UNPROVEN on device.**

### ⚠️ The row-key trap (found by the test suite, not by me)
I first made `RowKeys.chat(id)` return a **bare** id. Three existing `chat_rows_test.dart` tests
went red — correctly: a chat and a channel are both Firestore doc ids, so a bare key lets
`ValueKey('X')` collide across kinds and Flutter reuses the wrong row element.
**The prefix belongs to the row key but not to the route.** `RowKeys.locationOf` strips `chat:`
and passes a bare id to `/chat/<id>`, so a push sent by an older client (bare id) still resolves.
Cheap lesson worth repeating: the prefix is a *collision guard*, not a *route segment*.

### Push for channel posts (new, cloud-side)
`functions/channel_push.js` (pure) + `notifyChannelPost` trigger in `index.js`.
Fan-out differs from a call: recipients come from the `followers` subcollection, capped at
`MAX_RECIPIENTS=2000`, author excluded, tokens read in batches of 250 accounts and sent as
multicast (≤500 tokens). `data.type` is `"message"` with `chatId: "channel:<id>"`, and
`RowKeys.locationOf` is the only reader of that prefix — one place, so the two sides cannot drift.
⚠️ **NOT DEPLOYED.** Same standing rule as `notifyIncomingCall`: no deploy without the Boss asking.
`verify_push.js` (renamed from `verify_call_push.js`) covers both contracts: **26 checks**, plain
`node`, no credentials. It reads the Dart constants out of the source, so a rename on either side
fails the check instead of failing in the field.

## Phase 4 — full audit (DONE). `AUDIT_REPORT_V2.md`. 370 tests green.

### 🔴 THE BIG ONE — `Channel.fromJson` threw on every Firestore read (introduced by MY Phase 3)
`Channel` has 4 date fields; Firestore returns 3 of them as `Timestamp`, not `String`.
`channelFromDoc` converted only `createdAt`/`lastUpdateAt`. `addPost` writes `lastMessageAt`
(:613) and `markChannelRead` writes `lastReadAt` (:658) as server timestamps → `fromJson` did
`json['lastMessageAt'] as String` on a `Timestamp` → **`_TypeError`, thrown, on read, every time.**
Blast radius: **any channel with a post broke the whole Chats tab** (the first screen, since
Phase 3 merged channels into it). Fixed at `channel_service.dart:1058-1059`.
`test/core/channel_timestamps_test.dart` (9 tests) — **verified 7/9 fail with the fix reverted**
(`type 'Timestamp' is not a subtype of type 'String'`). Test written first, run red, then fixed.
**Scope:** every other model (Chat/Message/Contact/Status/Group) deserialises from Hive only —
`local/database/` — never a raw Firestore doc. `Channel` is the only model crossing that boundary,
so it is the only one that was wrong. Don't go "fixing" the others.

### 🔴 Each model's `fromJson` reads ISO strings; the converter must normalise EVERY date
New date field on a Firestore-backed model ⇒ add it to the conversion map, or you get a throw
(not a null) on read. This is the general form of the bug above.
