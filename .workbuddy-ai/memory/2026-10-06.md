# 2026-10-06 — email auth removal, device ringtone, chat-delete fix, publish-ready

## What was asked
One directive, eight phases, no questions, no local build: fix chat delete (optimistic + a deleted-chat
index), remove email auth entirely, add a device ringtone for incoming calls, delete the View Logs /
developer menu, verify notifications, make it publish-ready, audit every screen, then push and report the
CI APK URL.

## Phase 1 — chat delete
Root cause was (b)+(e) from the directive: the Firestore mirror re-added the row on its next snapshot
because nothing local remembered the removal, and `liveChatsStreamProvider` only emitted on a Firestore
snapshot, so a purely local act never reached the UI.

- `LocalChatRepository` gained a `deleted_chats_<uid>` index in `boxMessages`, a uid-keyed cache, a public
  `isDeleted()`, filtering in `_sorted`, and refusals in `save`/`saveAll`/`findById`/`_mutate`. Same shape
  as the message store's `deleted_ids_<chatId>` — two shapes of one problem should not have two solutions.
- `_liveChats` in `remote_chats_sync.dart` became a `StreamController` driven by `repo.watchAll()`, with
  the Firestore mirror as a side subscription.
- `deleteChat` is optimistic with the four exact log strings the directive named, and the remote leg is
  `unawaited`.
- ⚠️ `chats/{chatId}` is **shared** between participants, so `deleteChatDocument` deletes it only when the
  caller is the sole participant. "Delete chat" means "remove it from mine", not "destroy it for both of us".

## Phase 1b — message delete was slow for a second reason
`findById` had been given an optional `chatId` hint, but `_mutate` had not — so "delete for everyone"
resolved the row instantly and then scanned every conversation on the device to write it. `_mutate` now
takes the same hint. Symptom to remember: the read gets fast and the write stays slow, which looks like the
fix never landed.

## Phase 2 — email auth
Removed the email forms from login/signup, deleted `otp_screen.dart` (+ its test), stripped
`signUpWithEmail`/`signInWithEmail`/`sendPasswordReset`/`sendEmailVerification`/`ActionCodeSettings` and the
`isEmailVerified` block from `firebase_auth_service.dart` (1275 → 1095 lines), dropped
`AppRoutes.otp`, and removed the `imo://verify-email` intent-filter.
⚠️ The two surviving `signInWithEmailAndPassword` calls are the **phone** path — phone auth is an
email/password account with a derived address (`p<digits>@phone.imolive.app`). Do not "clean those up".

## Phase 3 — device ringtone
⚠️ **`playRingtone({volume, looping, asAlarm})` DOES exist in `flutter_ringtone_player` 4.0.0+4.** An
earlier reading of pub.dev concluded it did not and planned to use `play(android:, ios:)` instead. Wrong —
read `lib/flutter_ringtone_player.dart` in the pub cache before believing a summary of the API.
`RingtoneService` is static, guarded by `_isPlaying`, and fails silently; the calls are async so
`catchError` is what actually swallows a plugin failure — a `try`/`catch` around the call catches nothing.
⚠️ `_begin()` runs from a **post-frame callback**, so the incoming branch needs a `mounted` guard. Without
it `setState` throws *and* `startIncoming()` runs after `dispose()` already called `stop()` — the phone
rings forever with no UI left to stop it. Found during the Phase 7 audit.

## Phase 6 — publish-ready
- `pubspec.yaml` `1.0.0+1` → `1.0.0+2`. ⚠️ `build.gradle.kts` reads `flutter.versionCode`/
  `flutter.versionName`, so pubspec is the single source of truth — do not hardcode either in Gradle.
- minSdk 24; compileSdk/targetSdk come from the Flutter plugin (API 36 on 3.47.3), deliberately not pinned.
- R8/minify re-verified **off**: there is no `proguard-rules.pro` in the module, so enabling it would ship
  a release with zero keep-rules.
- Rewrote the 2-line README.
- ⚠️ **Still shipping `AppSecrets.r2SecretAccessKey`** — a real R2 secret with read/write/delete on the
  media bucket, compiled into the APK and used by `storage_service.dart`. Rotating it is a Cloudflare
  console operation, not a code change. Same for the public Metered TURN relay. **This is the one item that
  genuinely blocks a public release.**

## Phase 7 — audit, and the l10n blind spot
⚠️ **`_l10n_scan`/`UI_ARG` did not include `value:`**, which is the slot `SettingsValueRow` uses — so the
entire settings surface read as localised while ~20 descriptive strings were hardcoded English. Adding
`value` to the slot list took the count from 9 to 30. Also added a short-all-caps exclusion to `NOT_PROSE`
so locale codes (`BD`, `IN`, `US`) are not mistaken for prose.
Fixed 16 sites (settings, profile, about, account, linked-devices, privacy) with 11 new ARB keys — the
other five already existed. ARB now 1601 keys, en/bn symmetric.
**Still hardcoded, deliberately:** notification titles in `call_signaling_service.dart` /
`firestore_chat_service.dart` (service layer, no `BuildContext`, and the recipient's locale is not knowable
at send time), and premium strings that interpolate money amounts (need ARB placeholders). Bare `'$count'`
values are numbers and correctly stay untranslated.

## ⚠️ The remote had diverged — 18 local commits were never pushed
`origin/main`'s tree equalled local `5a67d79`'s tree, i.e. the remote carried only the **API-created**
lineage and was missing 18 local commits — including the CI apksigner verification, the
`assertReleaseSigning` guard and the whole `build-apk.yml` rewrite. Diagnosed by comparing **trees**, never
commits. `git fetch` and `git push` both work now (the old "push hangs" trap did not reproduce); the push
was rejected as non-fast-forward, so the fix is `git rebase --onto origin/main 5a67d79 main` — safe because
the two bases have identical trees, so the replay is conflict-free.
