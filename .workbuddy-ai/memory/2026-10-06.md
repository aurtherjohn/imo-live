# 2026-10-06 — email auth removal, device ringtone, chat-delete fix, publish-ready

## What was asked
One directive, eight phases, no questions, no local build: fix chat delete (optimistic + a deleted-chat
index), remove email auth entirely, add a device ringtone for incoming calls, delete the View Logs /
developer menu, verify notifications, make it publish-ready, audit every screen, then push and report the
CI APK URL.

## Phase 1 — chat delete
Root cause was (b)+(e) from the directive: the Firestore mirror re-added the row on its next snapshot
because nothing local remembered the removal, and `liveChatsStreamProvider` only emitted on a Firestore
snapshot, so a purely local act never reached the UI.

- `LocalChatRepository` gained a `deleted_chats_<uid>` index in `boxMessages`, a uid-keyed cache, a public
  `isDeleted()`, filtering in `_sorted`, and refusals in `save`/`saveAll`/`findById`/`_mutate`. Same shape
  as the message store's `deleted_ids_<chatId>` — two shapes of one problem should not have two solutions.
- `_liveChats` in `remote_chats_sync.dart` became a `StreamController` driven by `repo.watchAll()`, with
  the Firestore mirror as a side subscription.
- `deleteChat` is optimistic with the four exact log strings the directive named, and the remote leg is
  `unawaited`.
- ⚠️ `chats/{chatId}` is **shared** between participants, so `deleteChatDocument` deletes it only when the
  caller is the sole participant. "Delete chat" means "remove it from mine", not "destroy it for both of us".

## Phase 1b — message delete was slow for a second reason
`findById` had been given an optional `chatId` hint, but `_mutate` had not — so "delete for everyone"
resolved the row instantly and then scanned every conversation on the device to write it. `_mutate` now
takes the same hint. Symptom to remember: the read gets fast and the write stays slow, which looks like the
fix never landed.

## Phase 3 — device ringtone
⚠️ **`playRingtone({volume, looping, asAlarm})` DOES exist in `flutter_ringtone_player` 4.0.0+4.** An
earlier reading of pub.dev concluded it did not and planned to use `play(android:, ios:)` instead. Wrong —
read `lib/flutter_ringtone_player.dart` in the pub cache before believing a summary of the API.
`RingtoneService` is static, guarded by `_isPlaying`, and fails silently; the calls are async so
`catchError` is what actually swallows a plugin failure — a `try`/`catch` around the call catches nothing.
⚠️ `_begin()` runs from a **post-frame callback**, so the incoming branch needs a `mounted` guard. Without
it `setState` throws *and* `startIncoming()` runs after `dispose()` already called `stop()` — the phone
rings forever with no UI left to stop it. Found during the Phase 7 audit.

## ⚠️ A rebase destroyed `.git/refs` — and how the push was recovered
`git rebase --onto origin/main 5a67d79 main` died with `could not mark as interactive: No such file or
directory`, and afterwards **`.git/refs/`, `.git/logs/` and `packed-refs` were gone** — git reported
`fatal: not a git repository` while `.git/` plainly existed. `is_git_directory()` requires `refs/`, so the
repo looked destroyed when only its refs were.

Worse, the **pack was incomplete**: a stale `multi-pack-index` referenced a pack that no longer existed, so
`git fsck` reported `failed to load pack entry` for hundreds of oids and the commit object I had just made
was unreachable. `git verify-pack` still said `ok` — it only checks a pack's internal integrity, never that
it holds a complete closure. Do not read that as "the objects are all there".

What actually saved it: **the working tree was never touched.** Recovery, in order:

1. Recreate the ref dirs by hand (`refs/heads`, `refs/tags`, `refs/remotes/origin`, `logs`) — without
   `refs/`, no git command works at all, not even `cat-file`.
2. `mv .git/index .git/index.damaged` and `git add -A` — a fresh index rebuilds **every** blob from the
   working tree as loose objects, which is what re-materialised the content the pack had lost.
3. ⚠️ `git add -A` on a fresh index **drops tracked-but-ignored files**. Four were lost:
   `android/gradle/wrapper/gradle-wrapper.jar`, `android/gradlew`, `android/gradlew.bat` and
   `_verify_phone_auth.mjs`. The first three are required by CI. They must be re-added with `git add -f`.
   Detect the loss by diffing the old and new indexes, not by eyeballing the build.
4. Compare `git write-tree` against the tree of the pre-incident commit — it matched only after the `-f`
   re-add, which is how the drop was caught.
5. `git commit-tree <tree> -p <remote-tip> -F _commit_msg.txt` + `git update-ref refs/heads/main` — this
   sidesteps the missing intermediate history entirely, because the remote only needs the final tree.
6. `mv .git/objects/pack/multi-pack-index` aside to silence the stale-index errors.

⚠️ **`origin/main` had moved again during the session** (5b56d32 → 6a62611, an API-created commit whose
tree equalled local `6d85039`). Always re-read the remote tip via the API before building the commit, and
re-diff the remote tree against the local tree (`git diff-tree -r --name-status <remote-tree> <local-tree>`)
to prove the change set is exactly yours and reverts nothing.

`git push` worked — the old "push hangs forever" trap did **not** reproduce this session. Result:
`6a62611..6a526bc main -> main`, and the remote tree `0688139c` is byte-identical to local.

## ⚠️ Run #44 was cancelled with no runner — not a code failure

`cancelled`, `runner_name` **empty**, **0 steps**, and a `BlobNotFound` for the job log. That signature means
GitHub never assigned a runner; nothing in the repo was even checked out. Do not go looking for a code bug
when `steps count == 0` and the runner name is blank — **re-run the workflow** (`POST
/actions/runs/{id}/rerun`, HTTP 201) instead. Run #40/#39 in this repo's history failed the same way.

⚠️ `/actions/runs/{run_number}` 404s — `run_number` is not the run id. Query by `head_sha`
(`/actions/runs?head_sha=<sha>`) and read `id` from the result.
