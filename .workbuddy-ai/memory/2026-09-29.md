# 2026-09-29 (later) — Voice/video calls failed: no runtime permission request

## Root cause

**`AgoraCallService` never asked Android for `RECORD_AUDIO` or `CAMERA`.** The
manifest declares both, but a declaration is not a grant: on Android 6+ (this app
is `targetSdk 36`) dangerous permissions are denied until requested at runtime,
and **nothing in `lib/` ever requested them for a call**.

Verified: `grep -rn "requestPermission\|Permission\." lib/` returns exactly two
files — `permission_service.dart` (the wrapper) and `audio_location_service.dart`
(location only). The call path had **zero** request sites.

### Why this appeared only when the project moved to Agora

`WebRtcCallService._openMedia()` calls `navigator.mediaDevices.getUserMedia(...)`,
and on Android `flutter_webrtc` makes that raise the OS prompt **implicitly**. The
WebRTC path therefore got its permissions for free, and the comment at
`webrtc_call_service.dart:247` ("No permission, or no capture device") shows the
author knew the failure existed — but the *prompt* was never the app's job there.

Agora's native SDK captures media itself and does **not** prompt. So the swap to
Agora silently dropped the only thing that had been asking. Nothing in
`AgoraCallService` replaced it. Voice calls joined a channel with no microphone;
video calls additionally had no camera, so `startPreview()` had nothing to show.

`POST_NOTIFICATIONS` (Android 13+) was the same story: `push_notification_service`
routes `PushKind.call` → `notification_service.showCall`, so a **backgrounded**
callee gets an incoming-call notification — and without the permission it is
silently dropped. The in-app ring is unaffected, which is why this was invisible
in foreground testing.

## Second finding: a tapped call notification could never open the call screen

`PushNotificationService._onOpenedApp` ignored `kind` completely:

```dart
if (payload.chatId.isEmpty) { debugPrint('...no chatId — no navigation'); return; }
onOpenChat?.call(payload.chatId);
```

A call has no `chatId` — it has a caller. So tapping an incoming-call
notification hit the `chatId.isEmpty` guard and **did nothing** (or, if the
payload happened to carry a `chatId`, opened the **chat** instead of the call).
`PushPayload` had no caller field at all, and `onOpenChat` was the *only*
callback, so there was no route to the call screen even in principle.

Fixed:
- `PushPayload` gains `callerId` (+ `caller_id`) and `isVideo` (+ `is_video`).
  `isVideo` accepts a real bool **and** the strings `"true"/"false"/"1"/"0"`,
  because FCM delivers everything as strings — the existing `_read` coerces to
  string, so a bool needed its own reader. Unreadable → `false`, never a throw.
- `PushNotificationService.onOpenCall(callerId, callerName, isVideo)` added;
  `_onOpenedApp` branches on `kind == call` **first** and returns, so a call tap
  can never fall into the chat path.
- `main.dart` wires `onOpenCall` to `appRouter.go` on the call route in
  **incoming** mode (`outgoing=0`), using the same query shape the shell's `_ring`
  already uses (`id`/`name`/`video`/`outgoing`).

## Third finding, and the one that HID the other two: the call screen erased the failure

`call_screen._begin()`:

```dart
await _calls.start(...);
if (mounted) setState(() => _state = CallSessionState.dialling);   // <-- clobber
```

`start()` can reach a **terminal** state before it returns — a denied permission,
a token-server failure and an engine failure all emit `failed` from *inside*
`start`. So the `setState` above overwrote that failure with `dialling`.

Consequence: the user saw **"Ringing…"** and never the reason. A missing
microphone permission was indistinguishable from a dead network, and the screen
just closed after the 700 ms hand-off. This is why the reported symptom was
"calls are failing" with no diagnostic — the two defects above were both being
silently erased by this one.

Fixed by nudging the state only if nothing has moved it yet:

```dart
if (mounted && _state == CallSessionState.idle) {
  setState(() => _state = CallSessionState.dialling);
}
```

**How it was found:** by writing a screen-level widget test. The service-level
tests all passed while the user-visible outcome was still wrong — a service that
correctly reports a failure is worthless if the screen discards it. Test the
outcome the user sees, not just the layer you changed.

`test/widgets/call_failure_ui_test.dart` — 3 tests: the reason reaches the UI, the
generic fallback when there is none, and the outcome is logged exactly once.
Harness notes that cost time: the screen ends a call via GoRouter extensions
(`context.canPop()`/`go`), so the test needs a real `GoRouter`; and it asserts
**before** the 700 ms hand-off, past which the screen navigates away and the text
is gone (then pumps past it so no timer is left pending).

## Every "offline" test run was secretly hitting the live network

### What was found

`dart_test.yaml` declared the `integration` tag and its comment claimed *"Those
are excluded from the default run"* — but the file contained **no exclusion at
all**. It was:

```yaml
tags:
  integration:
```

`exclude_tags` appeared in the repo only inside comments. `run_flutter.sh` passes
no `--exclude-tags`. So the three tagged files
(`agora_token_integration_test.dart`, `agora_two_peer_integration_test.dart`,
`r2_public_fetch_integration_test.dart`) ran in **every** default `flutter test`.

Proof — the live markers appear in each prior "offline" run:

```
--- .t.log ---   1        (TWO PEERS OK / LIVE WORKER OK / R2 PUBLIC)
--- .t2.log ---  1
--- .t3.log ---  1
```

So the suite was neither offline nor deterministic, which is precisely what the
file's own comment said it was protecting against.

A second, subtler miss: my first grep for the tag used
`@Tags(\['integration'\])` and returned nothing. The files actually write
`@Tags(<String>['integration'])` — the **explicit type argument** defeats the
literal pattern. Grep for `@Tags` alone.

### Why `exclude_tags` was the wrong fix

Read from the installed packages (`test_core-0.6.18`, `test-1.31.1`), not from
docs:

1. **`Configuration.merge` unions `excludeTags`** (`configuration.dart:1029`):
   `excludeTags: excludeTags.union(other.excludeTags)`. The CLI config and the
   file config are merged by union, and union is commutative — so **no CLI flag
   can lift an exclusion written in `dart_test.yaml`**. `--exclude-tags none`
   parses as a tag literally named `"none"` (`boolean_selector` treats a bare
   identifier as a variable), which changes nothing. The comment's documented
   escape hatch, `--tags integration --exclude-tags none`, therefore **could
   never have worked**.
2. **`loader.dart:196` drops an excluded suite at load**: `if
   (_config.excludeTags.evaluate(...)) { return; }`. Not "skipped" — *dropped*.
   It never becomes a test entry, so `--run-skipped` cannot recover it and it
   does not even show up as skipped. The tests would silently cease to exist,
   which is the same silent-success failure class as `flutter.bat` and the APK
   with no `libapp.so`.
3. A tag-level `skip:` on the tag definition is worse: unconditional, so
   `--tags integration` prints "All tests skipped".

### The fix: `skip:` + `--run-skipped`

Verified from source that this pair is genuinely reversible:

* `engine.dart:344` — `var skipGroup = !suiteConfig.runSkipped &&
  group.metadata.skip;` and `:369` — `else if (!suiteConfig.runSkipped &&
  entry.metadata.skip) { await _runSkippedTest(...) }`. With `runSkipped` true
  the test falls through to the `else` branch and **actually runs**.
* `engine.dart:347` — `if (!skipGroup && group.setUpAll != null)`: a skipped
  group **never runs its `setUpAll`**, so nothing touches the network.
* `flutter test` exposes `--run-skipped` (`commands/test.dart:126`) and forwards
  it (`test/runner.dart:90`).
* `grep -rn "skip:" test/` → **0 hits**, so `--run-skipped` drags nothing else in.

Applied to all four network-touching groups across the three files, each with a
shared `_liveSkip` const carrying the exact command. The R2 file's first group
(`the public R2 base URL`) is hermetic — it only reads `R2Config` — so it stays in
the default run; only the fetch group is gated.

Demonstrated both directions:

```
# default run — gate holds, nothing hit the network (00:00, no `DART ->` line)
00:00 +1: the public R2 base URL is actually configured
00:00 +1 ~4: ... Skip: Live network test — run with: ... --run-skipped
00:00 +1 ~4: All tests passed!

# on demand
00:04 +5: All tests passed!      # 200s, correct content-types, cf-ray present
```

### Also established: an env-var gate would NOT have worked

`flutter_tester_device.dart:135` spawns the test process with a **hand-built**
environment map — `FLUTTER_TEST`, `FONTCONFIG_FILE`, `SERVER_PORT`, `APP_NAME`,
plus optional `FLUTTER_TEST_IMPELLER`/`UNIT_TEST_ASSETS`/`PATH`. A custom
`LIVE_TESTS` var is **not inherited**, so an env-var gate would silently never
fire — a false negative that looks like a passing hermetic suite. The two gates
that do reach the test are `skip:` and `--dart-define`
(`test_compiler.dart:122` passes `buildInfo.dartDefines` into the compile, so
`bool.fromEnvironment` works).

### `dart_test.yaml` now documents the real mechanism

It keeps `tags: integration` purely as a label and explains why `exclude_tags` is
not used, so the next person does not "fix" the missing exclusion back in.

## Microphone leak — "can't record a voice note, there's no call up"

Reported as: the app says recording is blocked "during a phone call" when no
call is active, blamed on an Agora engine never shut down after a failed call.

**The reported string does not exist.** `grep -rn "phone call|during a phone
call|Can't record"` over `lib/`, `test/`, `android/`, `assets/` and both `.arb`
files → nothing. It is a paraphrase, so the cause was only *inferable*.

**Two of the three items in the directive named things that are not there.**
`RtcEngine` has **no `destroy()`** in 6.6.4 — the releasing call is
`release({bool sync = false})` (`agora_rtc_engine.dart:6836`). And
`AgoraCallService.dispose()` already existed. Worse, item 2's premise — a
boolean call-active flag gating recording — was **false**: `AudioRecorderService.start()`
had no call-state check at all, and neither did `message_composer.dart`. The
mic button was simply refused by Android. Inventing a flag to "fix" would have
been a fiction.

### The real leak

Three defects, none of them the one described:

1. **`_join()`'s catch** — `enableAudio()` (line 620) opens the capture
   *before* `joinChannel()`, so a join that threw left the **singleton** engine
   holding the mic. No `leaveChannel`, no `release`, `_engine` still non-null.
   **This is the reported bug.**
2. **`_leave()`** called `leaveChannel()` but never released the engine and
   never nulled `_engine` — so even a clean hang-up kept the capture.
3. **`dispose()` never ran** in normal use: it was wired to `ref.onDispose`,
   which fires only on container teardown, not when a screen is popped. And
   `call_screen.dispose()` never touched `_calls` at all, so leaving by the
   system back gesture left the session live.

### Fix

- `_teardownEngine()` — the **single** teardown path: nulls `_engine` *first*
  (so the `onLeaveChannel` callback's deferred teardown is a no-op rather than a
  second release of a dying engine), then `leaveChannel()` + `release()`.
  Idempotent; returns the in-flight future so a caller arriving mid-release
  waits instead of racing.
- `_teardownAfterCallback()` — defers teardown off the SDK callbacks on a
  microtask, with an `identical` guard so a queued teardown cannot kill an
  engine a newer call has created. The SDK's own docs warn `release` inside a
  callback can deadlock.
- `_ensureEngine()` awaits `_teardownInFlight` before building: the SDK permits
  **one engine per App ID**, so creating the next while the previous is still
  releasing can fail outright.
- Called from: both `_join()` failure paths, `_leave()` (so hang-up/decline/ring
  timeout all release), `dispose()`, and the `onUserOffline` / `onLeaveChannel` /
  `onError` callbacks.
- `call_screen.dispose()` now ends a still-live session (decline if ringing and
  incoming, else end). It does **not** call `_calls.dispose()` — that service is
  a provider-scoped singleton and closing its controllers would silently kill
  every later call.

### Item 2, done honestly

There was no flag to remove, so instead of inventing one: `CallService` gained
`bool get holdsMicrophone`, derived from live state in all three implementations
(`_engine != null`; WebRTC `_localStream != null`; the simulator `false`).
`AudioRecorderService` takes a `bool Function()? callHoldsMicrophone` probe,
read **at the moment of failure**, used only to *explain* — never to pre-empt —
a refusal the platform already produced. It turns an unreadable native enum into
"the microphone is still held by a call. Hang up and try again." Pre-empting
would have invented a block that does not exist.

### Verification

New `test/core/microphone_release_test.dart` (11 tests) — the leak was invisible
to tests because `_ensureEngine()` could not be reached without a platform
channel. Added a `@visibleForTesting engineFactory` seam so a fake `RtcEngine`
(abstract → `implements` + `noSuchMethod`) can prove release on every terminal
path, that a token failure releases a half-built engine, that `dispose()` is

next one.

## The ring could fail silently — fixed

`watchIncoming(uid)` ended with `.handleError((error) { debugPrint(...); })`. A
`handleError` callback that returns normally **marks the error handled**, so the
`StreamProvider` never became `AsyncError`; the shell's listener saw an empty
list and did nothing. A failing ring listener therefore looked exactly like "no
one is calling" — and the user's conclusion, once already, was "calls are
broken". Two independent defects:

1. **The error was swallowed** — invisible in the UI, visible only in logcat.
2. **A Firestore snapshot stream closes when it errors**, and nothing
   re-subscribed. So a *transient* failure (a moment offline) killed the ring for
   the rest of the session. Silence plus permanence.

### Fix

- `CallSignalingService.retrying<T>(open, {attempts, delay, onError})` — re-opens
  the source on error, bounded (`ringAttempts = 3`), then **rethrows** so the
  provider surfaces `AsyncError`. A permanent cause (missing index, rules denial)
  now costs 3 quick failures and then becomes visible. Visible beats silent.
- `CallListenerBanner` (`features/calls/presentation/widgets/`) — a persistent
  strip at the top of the shell, mounted *before* `_ConnectivityBanner`, keyed off
  `incomingCallsProvider.error`. Persistent rather than a snack bar because the
  condition lasts until it is fixed, mirroring the existing offline banner.
- 9 new tests: `test/core/call_signaling_retry_test.dart` (5, pure) and
  `test/widgets/call_listener_banner_test.dart` (4).

### ⚠️ `yield*` does NOT throw into the generator — use `await for`

The first implementation delegated with `yield* open()` inside `try`. It did not
retry: **an error from a `yield*` source is forwarded to the consumer and the
`yield*` expression completes normally**, so the surrounding `catch` never fires.
`await for (final v in open()) { yield v; }` *does* rethrow at the `await for`,
where it can be caught. The symptom was a test asserting `opened == 3` getting
`1`. Cost one full test cycle — check for this whenever a retry loop "does
nothing".

### Also

- `StreamProvider` has **no `overrideWithValue`** in riverpod 2.6.1; use
  `overrideWith((StreamProviderRef<T> ref) => stream)`. And
  `AsyncValue.error(error, stackTrace)` needs the stack trace **positionally** —
  it is not optional in 2.6.1.
- `watchCall(callId)` still swallows its error the same way. Left alone on
  purpose: it is the **WebRTC** signalling path, which is not the configured
  provider (Agora is), and changing it would alter untested WebRTC behaviour.
  Flagged, not fixed.

## FCM sender written (the last functional gap for calls)

The in-app ring is a Firestore listener, so it only runs while the callee's app
is alive. A backgrounded or killed callee was never told a call was happening —
the caller heard it ring out and the callee's phone stayed silent. Not fixable
client-side; it needs a server watching `calls/`.

**New files** (`functions/`):

- `call_push.js` — the pure message contract, no Firebase import, so it is
  verifiable without credentials or an emulator.
- `index.js` — `notifyIncomingCall`, an `onDocumentCreated('calls/{callId}')`
  trigger: filters to `status == 'ringing'`, reads `users/{uid}.fcmTokens`
  (array — the client writes it with `arrayUnion`), sends a high-priority
  notification+data message, and prunes tokens FCM reports as permanently dead.
- `verify_call_push.js` — `node verify_call_push.js`, 12 checks, all passing.

**The verifier reads the Dart constants out of the app source** rather than
retyping them, so a rename on either side fails the check instead of failing in
the field: `PushKind.call` → `type`, `PushPayload`'s key constants → the `data`
keys, `NotificationChannels.calls` → `android.notification.channel_id`. That is
the whole value of it — a payload that arrives and is silently ignored looks
exactly like a push that never arrived.

Contract points that are easy to get wrong and are now pinned by a test:
- every `data` value must be a **string** (FCM rejects the whole message
  otherwise; `isVideo` is `"true"`/`"false"`);
- the channel is `imo_calls`, **not** `imo_messages`;
- only *permanent* FCM failures prune a token — `messaging/internal-error` and
  quota errors must not, or one bad minute silently unsubscribes a device;
- `ttl` is 45 s, matching the app's `ringTimeout`, so a late push cannot ring a
  phone for a call that is already over.

⚠️ **`functions/.eslintrc.js` sets `parserOptions.ecmaVersion: 2018`**, so
optional chaining (`?.`) and nullish coalescing (`??`) are *parse errors* under
`npm run lint` even though the runtime is Node 24. Written out longhand on
purpose; do not "modernise" it without changing that setting. `google` style
also enforces `max-len: 80` and double quotes.

## Round 5 — `watchCall` was the ring bug again, in a worse place

Request 7 item 1 also said *"ensure Firestore call signalling works with the
WebRTC flow"*, which I had only verified by reading. Auditing it found the same
silent-failure class already fixed on the ring path, plus two live answers.

### The bug
`CallSignalingService.watchCall` used `.handleError((e) { debugPrint(...); })`.
A handler that returns normally **marks the error handled**, so the error
vanished, the Firestore snapshot stream **closed**, and
`WebRtcCallService`'s `_callSub` simply stopped delivering — with **no `onError`
on the listener either**, so nothing surfaced anywhere. Symptom: the phone rings,
the callee accepts, and the call hangs on "Ringing…" forever because the SDP
answer and the ICE candidates never arrive.

### The fix
- `watchCall` now goes through the existing `retrying<T>` (3 attempts, then
  **rethrows**), exactly like `watchIncoming`. Split out as
  `@visibleForTesting watchDocuments(open)` so the policy is testable with **no
  Firestore instance** — the opener is the only part that needs one, and a test
  can hand it a `Stream.error`.
- Both `.listen()` calls gained `onError: (e) => unawaited(_onSignalingLost(e))`.
- `_onSignalingLost` **ends** the call rather than emitting `failed`, when the
  peer connection had come up. Media is P2P and survives the listener dying, but
  the listener is the only way a remote hang-up arrives. `failed` was rejected
  deliberately: the screen writes its log and pops on `failed`, while media is
  released only by the teardown that `ended` runs — so `failed` with a live mic
  would leak the microphone, the bug already paid for once.
- Both `on Object catch` blocks in `start()`/`acceptIncoming()` now
  `_finalise(CallStatus.missed)`, so a failure after `createCall` cannot leave
  the document on `ringing` with the callee's phone still ringing.
- New verifier literal: `"Lost the connection to the call"` — emitted only by
  `_onSignalingLost`, so finding it in `libapp.so` proves the fix shipped.

### Firestore, verified by measurement rather than by reading
`_fstest/dump_rules.py` refreshes the already-authenticated firebase-tools token
and reads the **deployed** ruleset:

    match /{document=**} { allow read, write: if request.auth != null; }

⚠️ **The whole database is open to any signed-in user** — every chat, call
record and profile. It is not in the repo (no `firestore.rules`; `firebase.json`
has no `firestore` section), so it is console-managed. Good news for this task:
signalling can never be *denied*, which rules out a rules block as a call-failure
cause. Bad news: it is the biggest outstanding risk in the project.

`_fstest/check_call_index.py` confirms the ring query's composite index is
**READY** (`receiverId ASC, status ASC, __name__ ASC`).

⚠️ **My own checker lied first.** It reported `NOT FOUND` because it demanded
exactly two fields — Firestore always appends `__name__`. Fixed, re-run, READY.
Same failure mode as the TURN control run: **a verifier I wrote produced a false
negative, and only a second look caught it.**

### The disk, and a purge I did not cause
The rebuild needed headroom and `C:` had fallen to **0.45 GiB**. I enumerated the
Recycle Bin (read-only) and asked, because emptying it is irreversible:
4.88 GiB was this project's own `tiger\build`/`dist` scratch, 3.65 GiB a Kali ISO
the user had deleted on 2026-08-31, 0.29 GiB Desktop items. **The user authorised
reclaiming the build scratch only.**

Then the decisive measurement: `$R` payload count was **0** and `C:` free was
**5.60 GiB**. **Windows had already auto-purged the Bin** because the volume hit
critical space — the Kali ISO went with it. Nothing I ran wrote anything (the
reclaim script was a dry run; `--apply` was never passed), but the user should
know their ISO is gone and that it was not me.

⚠️ **Recycle Bin `$I` metadata is not a stable measurement on this host** — the
same entries reported 158 MB in one run and 0 in the next, and two SID folders
went from readable to access-denied. Physical `$R` bytes are the only trustworthy
number. Do not base a destructive decision on `$I`.
