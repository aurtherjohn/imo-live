# 2026-09-27 — Profile bug fix, swipe-to-reply, and a refused directive

## "User Not Found" on profile tap — root cause and fix

**Symptom:** tapping a chat avatar (chat list or chat header) showed
"Contact not found".

**Root cause:** `Chat.id` is the *composite* `uidA_uidB` produced by
`FirestoreChatService.chatIdFor`, **not** a uid. Three call sites passed `chat.id`
to `/contact/:id`, which resolves `users/{uid}` — so the lookup always missed.
The signup flow was never at fault: `FirebaseAuthService._createUserDocument`
already writes `users/{uid}` plus the `usernames/` `emails/` `phones/` indexes for
both email and OAuth signups.

**Fix — `Chat.peerUid(selfUid)` in `lib/core/models/chat.dart`** is now the single
authority for turning a chat back into a peer uid. It returns null (never a
guess) when: not a direct chat, `selfUid` empty, `selfUid` not in `memberIds`
(chat mirrored from another account), or the members don't resolve to exactly one
other person. Added `Chat.isDirect` alongside it.

Call sites repaired to use it:
- `chat_screen.dart` → `_openChatInfo` (chat header + "View contact" menu item)
- `chats_screen.dart` → `_openProfileFor` (avatar tap; previously fell back to
  `chat.id` when `memberIds` was empty — the actual trigger)
- `chat_screen.dart` → `_startCall`

**Regression test:** `test/core/chat_peer_uid_test.dart` (9 tests) pins the happy
path plus every ambiguous case, including an explicit assertion that the result
is never the composite chat id.

## Two more bugs found in the same "wrong identifier" family

1. **Video calls always started as voice calls.** `router.dart` parsed the call
   route with `queryParameters['video'] == '1'`, but every caller builds the URL
   with `video=$isVideo`, which Dart renders as `true`/`false`. `== '1'` was
   therefore never true. Parser now accepts `'1' || 'true'`.
2. **Call signalling wrote a bogus receiver.** `_startCall` passed `chat.id` into
   the `calls/{callId}` document's `receiverId`, which is meant to be a uid.

## E2EE for 1:1 chats — implemented

`cryptography ^2.7.0` (resolved 2.9.0, pure Dart so it is unit-testable) and
`flutter_secure_storage ^10.0.0` added. **Pin flutter_secure_storage to the 10.x
line** — declaring `^9.2.4` downgraded it and its four platform implementations
underneath whichever plugin pulled it in as a transitive dep.

New `lib/core/services/e2ee_service.dart`:
- `E2eeEnvelope` — `{v, alg, sk, n, c, m}`, all base64url, stored in the message's
  `text`. `tryDecode` returns null rather than throwing (an old plaintext
  message and a corrupt payload must both degrade, not crash).
- X25519 key exchange → 32-byte shared secret → AES-256-GCM, fresh 12-byte
  nonce per message. `SimpleKeyPairData(private, publicKey: SimplePublicKey(...,
  type: KeyPairType.x25519), type: KeyPairType.x25519)` is how a stored key pair
  is rebuilt — `newKeyPairFromSeed` is not reliable here.
- Private key in the platform keystore under `imo_e2ee_private_key`; public key
  published to `users/{uid}.e2eePublicKey`.
- **The sender's public key travels in the envelope**, not looked up from
  `users/{uid}` — otherwise a message read *after* the sender rotates keys
  derives the wrong secret.

Wiring (`firestore_chat_service.dart`):
- `sendMessage` gains `String? peerUid`. Sealing happens **at the Firestore
  write**, the last point plaintext exists, so the local cache and the on-screen
  bubble keep readable text. `e2ee: true` is written explicitly, and
  `lastMessage` becomes `E2eeService.sealedPreview` so the chat-list preview
  does not leak either.
- `watchMessages` switched `.map` → `.asyncMap` and opens sealed bodies. It does
  **not** fail open — an unopenable body shows `undecryptablePreview`, never raw
  ciphertext.
- `peerUid` is threaded `chat_screen → ChatService.sendMessage → _publishRemote`.
  `Chat.peerUid()` returns null for groups, which is exactly the "don't encrypt"
  signal.
- `FirestoreChatService` is no longer `const`; `firestoreChatServiceProvider`
  injects `e2eeServiceProvider`. Identity is ensured/reset from
  `AuthController.build()` off `authStateProvider`.

`test/core/e2ee_service_test.dart` (13 tests): round-trip, nonce uniqueness,
tamper detection via the GCM MAC, third-party cannot open, no-key → fail open,
reset. Uses a `_MemorySecureStorage extends FlutterSecureStorage` fake — note
the override signature uses **`AppleOptions`** for both `iOptions` and
`mOptions` in 10.x (not `IOSOptions`/`MacOsOptions`).

### Deliberately NOT done — do not claim otherwise
No forward secrecy (one static shared secret per conversation; a leaked key opens
every past message), no MITM protection (public keys are trusted from Firestore —
a lying server can sit in the middle), and no group support. Each has a
`// TODO:` in the service's class dartdoc. Sending fails **open** to plaintext
when a peer has no key.

## Build fix: `android/jvm_target.gradle` (new file, applied from build.gradle.kts)

`:flutter_facebook_auth:compileReleaseKotlin` started failing with
`Inconsistent JVM-target compatibility ... compileReleaseJavaWithJavac (11) and
compileReleaseKotlin (25)`.

- **Why it appeared now:** it was latent. Bumping `flutter_secure_storage`
  (a dep of `flutter_web_auth_2`, which `flutter_facebook_auth` consumes)
  invalidated that module's compile classpath and forced a recompile for the
  first time in months. Nothing about the plugin changed.
- **Why Kotlin was 25:** KGP 2.4.0 infers `jvmTarget` from the Gradle JDK when a
  module does not set one. The app module sets 17 explicitly; plugin subprojects
  do not.
- **Fix:** a subprojects script pinning Kotlin `compilerOptions.jvmTarget` to 17
  and Java `source/targetCompatibility` to 17.
- **Gotcha worth remembering:** configuring `JavaCompile` tasks eagerly does NOT
  stick — AGP rewrites source/target compatibility when it configures each
  variant, after the root project has run. The first attempt still reported
  Java 11. It has to set `android.compileOptions` (and the tasks) inside
  `afterEvaluate`. Mirror the style of the existing `compile_sdk.gradle`.

## WebRTC voice/video calls — signalling + media implemented

`flutter_webrtc ^1.6.2+hotfix.3` added.

New `lib/core/services/call_signaling_service.dart`:
- `CallDocument` over `calls/{callId}`: `{callerId, calleeId, isVideo, status,
  offer, answer, callerCandidates[], calleeCandidates[], createdAt}`. One
  document, not a subcollection per signal — a call is a handful of small
  writes and `watchCall` then delivers everything in one ordered stream.
- `CallDocument.fromMap` is split out of `fromDoc` **because a
  `DocumentSnapshot` cannot be constructed in a unit test** — that is the half
  worth testing.
- `hasOffer`/`hasAnswer` require both `type` and a non-empty `sdp`; a
  half-written session reports as absent rather than making the peer call
  `setRemoteDescription` with garbage.
- `watchIncoming(uid)` filters to `status == ringing` so an answered or ended
  call cannot resurrect a ring.

New `lib/core/services/webrtc_call_service.dart`:
- `WebRtcCallService implements CallService, VideoCallStreams` — real
  `getUserMedia` → `RTCPeerConnection` → offer/answer → ICE, with candidates
  swapped through Firestore. Media is peer-to-peer; Firestore only carries SDP.
- `WebRtcIce`: STUN/TURN from `--dart-define` (`CALLS_STUN_URL`,
  `CALLS_TURN_URL/USERNAME/PASSWORD`), defaulting to Google's public STUN.
  **No TURN is configured**, so two peers on mobile networks will negotiate and
  then never connect — that is the documented TODO, not an oversight.
- `_appliedCandidates` set keyed on the candidate string: Firestore re-delivers
  the whole array on every snapshot, so without it candidates are added twice.
- `VideoCallStreams` is a separate optional interface, so `LocalCallService`
  does not have to depend on `flutter_webrtc`.

Call screen (`call_screen.dart`):
- `_VideoLayout` takes `remoteVideo`/`localVideo` widgets and uses them in place
  of the avatar placeholder; `RTCVideoView` is only built when
  `renderer.srcObject != null`, because an empty renderer paints solid black,
  which is worse than the placeholder.
- The "Local simulation" banner is now gated on `_isSimulated`, so a real call
  no longer shows a warning that contradicts itself.

`callServiceProvider` returns `WebRtcCallService` when a session exists, else
`LocalCallService`. It reads the uid from a new `callUidProvider` in
`providers.dart` rather than `currentUidProvider`, because `auth_providers.dart`
already imports `providers.dart` and reaching back would be circular.

Manifest: added `BLUETOOTH_CONNECT` (+ legacy `BLUETOOTH`/`BLUETOOTH_ADMIN` for
API ≤ 30). Without it the WebRTC audio session cannot route to a headset on
Android 12+.

**Not done:** no incoming-call ring screen (the service and
`incomingCallsProvider` exist, nothing consumes them yet), no ring timeout to
`missed`, no ICE restart on network change.

Created with the PowerShell tool (`New-Item -ItemType Junction -Path <p> -Target <t>`);
verify with `ls -ld <path>` (shows `-> /f/...`) and a write-through test. Rename the

### CORRECTION — the `F:` escape hatch does NOT work for Gradle caches

The junction idea is sound for *space*, but `F:` is unusable for
`.gradle_home` because **the sandbox caps a directory at 16 384 entries on `F:`**:

```
Could not open cache directory … (F:\tiger-gradle-home\caches\9.3.1\transforms\<hash>)
> Cannot create directory '…\<hash>'.
```
and from the shell, on the same path:
```
mkdir: cannot create directory '…': Operation not permitted     # EPERM, not ENOSPC
```
`16384 = 2^14` exactly, reproduced independently by `robocopy` (which stopped at
16 384) and by Gradle. `C:`'s equivalent directory holds **16 851** and works, so the
cap is per-`F:`/policy, not a filesystem-wide or space limit. A fresh directory on
`F:` creates fine — it is that one directory's entry count that is capped.

**Conclusion: keep `GRADLE_USER_HOME` on `C:`.** Only the project `build/` tree is
junctioned to `F:` (that part is fine and buys the space).

### You cannot free `C:` space from the tool layer — at all

Every deletion path is intercepted and moved to the Recycle Bin instead of
unlinked. Confirmed three ways this session:

1. `rm -rf build/app/intermediates` — build/ shrank 1.3 G → 392 M, bin entries
   36 547 → 36 553, `df` **512 M → 511 M**.
2. PowerShell `Remove-Item -Recurse -Force` on a 392 MB dir — `df` **354 → 352 M**.
3. That same `Remove-Item` was itself blocked by the shim:
   `[safe-delete][SAFE_DELETE_BULK_GUARD_ERROR] bulk delete guard blocked deletion`.

So the Bash `rm` shim is not the only interceptor — PowerShell's `Remove-Item` is
hooked too. **The Recycle Bin is the only place space can be reclaimed from, and
emptying it is a user action** (`Clear-RecycleBin -DriveLetter C -Force`, or
right-click → Empty Recycle Bin). Verified PowerShell itself is healthy, so the
command will work — a large bin takes ~15 min, run it in the background.

### Recovering from a botched `robocopy /MOVE`

`/MOVE` deletes source files it copied — but when the copy *fails* (the 16 384 cap)
you can be left with both sides incomplete. Recovery that worked:

- The **global `~/.gradle`** was the intact source of truth for the wrapper
  distribution — `~/.gradle/wrapper/dists/gradle-9.3.1-all/…` had `gradle-9.3.1/`,
  the 234 MB `.zip`, and `.zip.ok`.
- `.gradle_home` on `C:` was restored by renaming the aside copy back, then
  `cp -r`-ing the seven small top-level items (`gradle.properties`, `init.d`,
  `native`, `daemon`, `android`, `kotlin-profile`, `notifications`) back from `F:`.
- To remove a junction without touching its target:
  `[System.IO.Directory]::Delete($path, $false)` — the `$false` keeps it from
  recursing. Verified: `isReparsePoint: True`, then the `F:` target was still intact.
  Plain `Remove-Item` on a junction risks deleting the target's contents.
- Reading a junction from Git Bash: `ls -ld` shows `-> /f/...`. Watch out — an
  `ls` of a *junction target* and of the *link* look identical; several of my
  earlier "the file is empty" readings were the wrong side.

### Even MOVING data off `C:` does not free space

Final proof, measured cleanly: `robocopy /MOVE` of `apk_backup/` (245 MB) to `F:`.

```
BEFORE: 288M free
robocopy RC=1        # moved, source removed (verified)
AFTER:  219M free    # went DOWN 69M, not up 245M
```

So it is not just the `rm` shim: **the interception is below the shell.** `del`,
`rd`, `Remove-Item`, and `robocopy`'s own native delete are all affected, and
nothing available from the tool layer reclaims `C:` space. Do not burn time
looking for a clever delete — there isn't one. **Emptying the Recycle Bin is the
only reclamation path, and it is a user action.**

Corollary: a half-finished "free some space" attempt can leave `C:` *lower* than
it started, which is exactly what happened repeatedly here (705 M → 512 → 361 →
288 → 219 M).

### Two things that will bite later
1. **`VideoCallStreams` is typed to `flutter_webrtc`** — its `RTCVideoRenderer`
   return type means no other provider can implement it. Agora renders through
   its own native view, so an optional `CallVideoSurface` interface (returns
   `Widget?`) was added to `call_service.dart` and the call screen type-checks
   both. A third provider should widen `VideoCallStreams` rather than add
   another interface.
2. **`R2Config.publicBaseUrl` was never supplied.** The dev credentials carry no
   bucket public URL, so `effectivePublicBaseUrl` falls back to
   `{endpoint}/{bucket}` — a SigV4-signed URL. Uploads succeed, but the links
   will NOT render on another device until `R2_PUBLIC_BASE_URL` is set (an
   r2.dev URL or a custom domain). `isConfigured` was deliberately decoupled
   from it so uploads are not silently disabled.

### Security notes
- Every value in `app_secrets.dart` is `static const` → plaintext in
  `libapp.so`, recoverable with `strings`. Revoke all of them before the APK
  leaves the machine.
- The `cfat_…` value is a Cloudflare **account** API token, not an R2 S3 key. It
  is NOT read by `R2Config` (S3 auth uses accessKeyId/secretAccessKey) and is
  the widest-scoped credential in the file.
- The Agora **app certificate** is a server-side secret. `AgoraCallService`
  deliberately does not read it — joins send an empty token (APP ID-only testing
  mode). Secured mode requires a token server; a client-side mint is the
  open-relay anti-pattern.
- `agora_rtc_engine`'s AAR declares `READ_PHONE_STATE`, which this project
  deliberately stripped. The manifest merger will re-add it; block it with a
  `tools:node="remove"` entry if that matters.

## R2 credentials verified against the live bucket

Rather than leave the R2 wiring as "it compiles", the credentials were tested
against the real bucket with boto3 (S3 SigV4, `region_name="auto"`,
`addressing_style="path"` — the same shape `R2Config` uses). The values are read
by regex straight out of `app_secrets.dart`, so the check covers the file that
actually ships rather than a copy.

**All four steps pass**: HeadBucket (authenticate) → PutObject → GetObject
(content matches) → DeleteObject (cleanup). The account id, access key, secret
key, bucket name and endpoint are therefore all correct, and the bucket is
writable. This closes the "StorageService updated and working" claim properly.

The `cfat_` token is **invalid**: `GET /user/tokens/verify` returns
`{"code":1000,"message":"Invalid API Token"}` (401), and every
`/accounts/{id}/r2/...` call returns 403. It is already revoked, expired, or
truncated. It is also unnecessary — S3 auth uses only the access-key pair. Delete
the line: it is a dead credential that *looks* live and invites a false sense of
exposure.

needs a working account token. `R2_PUBLIC_BASE_URL` still has to be set by hand
from the Cloudflare dashboard. Until then uploaded links are SigV4-signed and
